## Requirements
### Requirement: Browser suite runs against deployment-shaped WASM output
The project SHALL provide a standalone Playwright Test and TypeScript suite that exercises the Blazor WebAssembly application in real browsers. The default target SHALL be the Release static output prepared for the GitHub Pages `/ChapterTool/` path. A local development-server configuration SHALL run the same scenarios at the root path for diagnosis.

#### Scenario: Test the prepared Release site under the repository path
- **WHEN** a developer prepares and runs the default browser suite
- **THEN** the suite serves the prepared Release site and navigates to `http://127.0.0.1:5261/ChapterTool/`
- **AND** framework assets load from the repository subpath without falling back to the page for missing resources

#### Scenario: Diagnose the application with the development server
- **WHEN** a developer runs the development browser configuration
- **THEN** Playwright starts the Blazor development server on the loopback address at the root path
- **AND** the same workflow assertions run without changing their expected behavior

### Requirement: Static site preparation is safe and deployment-consistent
The preparation step SHALL transform a single Release publish into a static site directory with the required Pages base path and deployment files. It SHALL validate that any directory it clears is within `artifacts/wasm-e2e/`. The static server SHALL bind only to loopback, serve correct MIME types including `application/wasm`, return 404 for missing resources, and prevent paths from escaping its configured root. GitHub Pages SHALL test and upload the same prepared directory without rebuilding or rewriting it after tests.

#### Scenario: Prepare static output for local browser testing
- **WHEN** the preparation script receives a valid publish directory
- **THEN** it creates the Pages-shaped site with the expected base path and static deployment files
- **AND** it does not delete files outside the validated E2E artifact directory

#### Scenario: Serve an asset and reject missing or unsafe paths
- **WHEN** the static server receives requests for a WASM asset, a missing framework asset, and a path outside its root
- **THEN** it serves the asset with `application/wasm`, returns 404 for the missing asset, and refuses the path traversal request

#### Scenario: Deploy the artifact that passed smoke tests
- **WHEN** the Pages workflow runs its pre-deployment smoke suite successfully
- **THEN** it uploads the same prepared site directory that the suite tested
- **AND** a failed smoke suite stops artifact upload and deployment

### Requirement: Browser tests use accessible user interactions and observable outcomes
The application SHALL expose accessible names and stable readiness semantics needed to operate and observe its browser workflows. The browser suite MUST prefer roles, labels, and scoped dialog locators over brittle CSS paths or coordinates. Readiness MUST be set after initialization, settings restoration, and JavaScript event registration, and MUST NOT substitute for an actual interop smoke action.

#### Scenario: Wait for application initialization and verify interop
- **WHEN** a browser test opens the application
- **THEN** it waits for the application readiness marker
- **AND** the smoke test imports a real file through the page before passing

#### Scenario: Commit and verify an edited chapter
- **WHEN** a test changes a chapter field and performs a real blur action
- **THEN** it verifies the committed table value and the corresponding undo/redo or exported result
- **AND** it does not pass based only on the value still present in the focused input

### Requirement: Browser workflows cover user-visible behavior and downloaded bytes
The suite SHALL cover the planned staged workflows: startup and import, chapter editing and history, preview and export, replacement confirmation, invalid input recovery, settings persistence and cancellation, localization, keyboard behavior, file boundaries, tab isolation, disc workflows, and responsive layout. Download tests MUST inspect the downloaded file's name and contents; encoding tests MUST inspect bytes. Expected exports MUST be fixed, reviewed fixtures and MUST NOT be generated by the implementation under test.

#### Scenario: Complete a core import, edit, history, and download workflow
- **WHEN** a test imports a known OGM fixture, edits a chapter, undoes and redoes the change, then saves
- **THEN** the table and history controls show the expected state
- **AND** the real downloaded file matches a fixed expected result

#### Scenario: Recover from invalid input without losing the current document
- **WHEN** a test imports malformed input while a document is open
- **THEN** the page shows a visible diagnostic and preserves the current document and history
- **AND** a subsequent valid import remains usable

#### Scenario: Verify localization and encoded output
- **WHEN** a test selects English, Chinese, or Japanese in the application and saves representative chapter names
- **THEN** visible labels and the applied document language match the selected locale
- **AND** the downloaded text decodes correctly, with byte-level checks for BOM and UTF-16 formats

### Requirement: Browser state boundaries and diagnostics are explicit
Each browser test SHALL start with an isolated BrowserContext unless it explicitly tests multiple pages in one context. Tests SHALL collect page errors, console errors, failed requests, and failed same-origin resource responses from before navigation, attach diagnostics, and fail on unexpected errors. Tests MUST interact through the page and MUST NOT call application internals or mock Core/WASM results.

#### Scenario: Detect unexpected startup and resource errors
- **WHEN** a test navigates to the application
- **THEN** its diagnostics capture page, console, request, and same-origin resource failures
- **AND** unexpected failures cause the test to fail with attached diagnostic output

#### Scenario: Verify independent chapter sessions across tabs
- **WHEN** two pages in the same BrowserContext edit separate documents
- **THEN** each page retains its own chapter and history state
- **AND** shared settings storage is not treated as chapter-session leakage

### Requirement: CI gates browser regressions and retains artifacts
Pull requests and relevant pushes SHALL run the implemented Chromium behavior suite. The Pages workflow SHALL run Chromium `@smoke` against the prepared deployment artifact before deployment. A scheduled or manually triggered acceptance workflow SHALL run the full suite in Chromium, Firefox, and WebKit. CI SHALL retain reports, traces, failure screenshots, logs, and downloaded files when a run fails or succeeds. Retried flaky tests SHALL remain gate failures.

#### Scenario: Run the Chromium pull request gate
- **WHEN** a relevant pull request or push changes the WASM application, its dependencies, browser suite, or build configuration
- **THEN** CI publishes and prepares the Release output and runs the implemented Chromium suite
- **AND** a failed test makes the job fail

#### Scenario: Run cross-browser acceptance
- **WHEN** the scheduled or manually triggered acceptance workflow runs
- **THEN** it executes the full browser suite in Chromium, Firefox, and WebKit
- **AND** it reports pass, failure, and skip counts for each engine

#### Scenario: Preserve diagnostics for failed CI runs
- **WHEN** an E2E job fails
- **THEN** CI uploads its reports, traces, screenshots, logs, and downloaded test files
- **AND** a test that passes only after retry remains a failure

### Requirement: Test setup and acceptance evidence are documented
The E2E README and repository testing ownership documentation SHALL explain prerequisites, install and run commands, browser installation, development mode, report viewing, and failure diagnosis. The WASM README and testing code map SHALL identify the suite and its ownership. The first acceptance report SHALL distinguish planned coverage from executed coverage and record the commit, locked dependency and browser versions, operating system, commands, per-engine outcomes, duration, and artifact paths.

#### Scenario: Set up the suite in a clean environment
- **WHEN** a developer follows the E2E README in a clean checkout
- **THEN** the developer can install locked dependencies, install the selected browsers, prepare the site, run type checking and tests, and open the report

#### Scenario: Record first acceptance results
- **WHEN** implementation reaches the first acceptance run
- **THEN** the report records the required environment and command evidence
- **AND** it labels unexecuted coverage as planned instead of passed
