# UI 视觉一致性排查与修复指导

## 目的

本方案用于排查和修复 Avalonia 界面的视觉不一致问题。适用范围包括工具栏、列表行、详情面板、状态栏、弹窗、Flyout、菜单、标签页和空状态区域。

排查目标不是让所有控件完全相同，而是让具有相同语义的控件遵循相同的视觉规则，让不同语义的控件使用独立且可解释的主题资源。

## 适用范围

在以下情况使用本方案：

- 新增页面或控件后，界面与现有页面的间距、尺寸或颜色不一致。
- 同一工作流在摘要、详情、弹窗或窄窗口下出现不同布局。
- 主题切换后出现固定颜色、错误背景或文字对比度问题。
- XAML 模板、样式或资源调整后，按钮、边框、圆角或 Padding 发生回退。
- 行为测试通过，但截图或实际渲染仍存在视觉回归。

## 核心原则

1. 先定义视觉基准，再判断偏差。基准必须包含布局结构、列定义、行高、Padding、Margin、颜色、边框、圆角、字体和控件状态。
2. 相同语义复用同一结构或样式。不要在摘要、详情和弹窗中复制近似的列定义和尺寸常量。
3. 颜色必须来自语义资源。不要用采样得到的近似色值替换主题令牌。
4. 先检查公共模板，再修改控件实例。优先确认 `ControlTemplate`、`TemplateBinding`、选择器和资源覆盖关系。
5. 每次聚焦一个视觉问题，并在修改后立即验证。避免把布局、颜色和行为改动混在一次排查中。
6. 以渲染结果作为证据。源码检查用于定位来源，Headless 和截图用于确认最终效果。

## 排查流程

### 1. 建立范围和基准

记录受影响的页面、控件和状态。为每类控件建立基准表，至少记录：

| 类别 | 需要记录的属性 |
|---|---|
| 布局 | Grid 列、对齐方式、MinWidth、行高、伸缩规则 |
| 间距 | Padding、Margin、控件之间的间隔 |
| 表面 | Background、Foreground、BorderBrush、BorderThickness、CornerRadius |
| 文字 | 字体、字号、字重、换行和截断规则 |
| 状态 | 默认、悬停、按下、禁用、选中、错误和空状态 |
| 操作 | 可见按钮数量、按钮尺寸、图标、可访问名称和键盘顺序 |

基准应来自当前主题资源和已确认的稳定页面，而不是来自单张截图中的像素猜测。

### 2. 追踪视觉属性来源

按以下顺序检查：

1. 页面和控件实例上的局部属性。
2. `Styles.axaml` 中的选择器和 `ControlTemplate`。
3. `Themes.axaml` 及其他主题资源文件中的 `Color.*` 和 `Brush.*`。
4. 运行时主题服务对资源的覆盖或转换。
5. 平台默认模板和第三方控件模板。

使用 `rg` 搜索资源键、模板和属性绑定。对每个异常属性记录“定义位置、覆盖位置、最终运行时值”三项证据。特别检查同一令牌是否被错误地用于不同语义，例如把工具栏背景用于状态栏或弹窗。

### 3. 建立同类控件清单

不要只修复发现问题的第一个实例。按语义列出全部同类控件，例如：

- 所有 Flyout 及其 `FlyoutPresenter`。
- 所有详情标题、摘要行和列表头。
- 所有关闭、返回、复制和更多操作按钮。
- 所有空状态、错误状态和进度状态区域。
- 所有主题和语言下的对应资源。

逐项比较结构、资源键和运行时属性。若多个实例需要相同修复，应抽取共享样式或模板；若语义不同，应定义独立的资源键。

### 4. 实施最小修复

- 先统一结构，再处理颜色和细节。
- 让详情或扩展视图复用基准布局，仅追加必要操作列。
- 为状态栏、内容区、工具栏和弹窗使用明确的语义资源。
- 删除重复边框层，确认外层和内容层的边界职责只有一个。
- 为固定格式区域设置稳定尺寸或 `MinWidth`，防止按钮、旋钮和文字相互覆盖。
- 确认文本替换命中了唯一节点，再修改 XAML。

### 5. 分层验证

每个修复至少完成以下验证：

1. 编译相关项目，确认 XAML、资源和绑定无错误。
2. 运行对应 Avalonia 单元测试和 Headless 测试，验证打开、关闭、筛选、命令和状态转换。
3. 在默认、宽窗口和窄窗口下生成截图，检查布局是否稳定。
4. 在支持的主题和语言下重复检查。
5. 对关键属性增加行为断言，包括 `Bounds`、高度、`Padding`、`CornerRadius`、`BorderThickness`、背景、前景和可见按钮数量。

截图用于发现和复核视觉差异。不要把截图文件存在作为唯一自动化断言；应同时提供运行时属性或像素检查的证据。

### 6. 资源和本地化检查

修改共享 Avalonia 本地化资源后，运行：

```bash
uv sync --project scripts
uv run --project scripts scripts/axaml-to-json.py
uv run --project scripts scripts/axaml-to-json.py --check
```

不要手工编辑生成的 Wasm JSON 文件。检查所有支持的语言是否具有相同的资源键，并确认长文本不会破坏按钮、标题和窄窗口布局。

## 问题记录模板

每个问题都应记录以下内容：

| 项目 | 内容 |
|---|---|
| 位置 | 页面、控件、文件和行号 |
| 现象 | 可观察的视觉或交互差异 |
| 期望 | 对应的视觉基准或设计规则 |
| 来源 | 局部属性、样式、模板或运行时资源 |
| 影响 | 主题、窗口尺寸、语言和用户操作 |
| 修复 | 最小改动及其共享范围 |
| 验证 | 测试命令、运行时属性、截图或像素证据 |

不要把“看起来不对”作为唯一证据。应给出可定位的属性、资源键、Bounds 或渲染差异。

## 验收标准

- 相同语义的区域具有一致的结构、间距、尺寸、颜色、圆角和状态表现。
- 不同语义的区域不复用会造成误解的主题令牌。
- 默认、宽窗口和窄窗口均无文字、按钮、表格列或旋钮重叠。
- 弹窗和 Flyout 具有一致且可解释的 Presenter、背景、边框和内部 Padding。
- 详情、关闭、返回和菜单操作符合预期，且只显示必要的操作按钮。
- 主题切换和所有支持的语言不会引入固定颜色、资源缺失或布局溢出。
- Avalonia 单元测试、Headless 测试和本地化资源漂移检查均通过。
- 发生视觉回归时，可以根据问题记录复现来源并定位到具体修复。

## 推荐验证命令

```bash
dotnet test tests/ChapterTool.Avalonia.Tests/ChapterTool.Avalonia.Tests.csproj --no-restore
dotnet test tests/ChapterTool.Avalonia.Headless.Tests/ChapterTool.Avalonia.Headless.Tests.csproj --no-restore
dotnet test ChapterTool.slnx --no-restore
```

涉及应用项目文件时，再运行：

```bash
dotnet build src/ChapterTool.Avalonia/ChapterTool.Avalonia.csproj --no-restore
```
